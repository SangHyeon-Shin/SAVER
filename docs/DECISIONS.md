# 기술 결정 기록

**"왜 이렇게 되어 있는가"에 대한 답입니다.**
같은 논의를 반복하지 않기 위해, 그리고 최종보고서를 쓸 때 근거를 다시 찾지 않기 위해
남깁니다. 결정을 뒤집을 때는 이 문서를 먼저 고치세요.

---

## 아키텍처

### D-01 · 상태머신의 주인은 Jetson 브리지다

**결정**: 운용 상태머신(S1~S13)은 Python 브리지가 소유한다.
UI 는 `intent` 를 보내고 받은 `state` 를 그리기만 한다.

**이유**: 레이더·카메라·PPG 판단 입력이 전부 Python 에 도착하는데,
상태의 주인이 브라우저에 있으면 판단과 화면이 어긋난다.
UI 를 새로고침해도 장치 상태가 바뀌면 안 된다는 요구사항과도 맞는다.

**예외**: 브리지 미연결 시 UI 가 로컬 전이로 대체한다. **오프라인 시연 전용**이며,
연결되면 즉시 브리지 판단으로 넘어간다.

### D-02 · 상태머신 정의는 파일 하나뿐이다

**결정**: `protocol/state_machine_v2.json` 이 유일한 기준.
Python 은 직접 읽고, UI 는 빌드 전에 자동 복사(`ui/scripts/sync-protocol.mjs`)한다.

**이유**: 처음에는 UI 와 Python 이 각자 전이표를 갖고 있었다.
한쪽만 고치면 조용히 어긋나고, 통합 시점에야 발견된다.

### D-03 · Jetson 은 실시간 제어를 하지 않는다

**결정**: 100~500 Hz 제어 루프는 Teensy 전담. Jetson 은 목표값만 보낸다.

**이유**: Linux 스케줄링, USB 지연, Python GC, UI 부하 때문에 제어 주기가 흔들린다.
`S2_데이터_수집처리_정의서` 에 기구 제어 데이터가 100~500 Hz 로 정의돼 있다.

**금지되는 구조**
```
Jetson 이 깊이를 읽음 → Python 에서 PID 계산 → 매 주기 Teensy 에 PWM 명령
```

### D-04 · 장치가 준비되지 않으면 화면이 넘어가지 않는다

**결정**: `state_machine_v2.json` 의 `requires_mcu` 로 전이 선행조건을 검사한다.

**이유**: 종단간 시험에서 실제로 발생했다. 흡착이 끝나기 전에 사용자가
[재확인]을 연타하니 UI 만 앞서 나갔다. 레이더·카메라가 붙으면 더 심해진다.

거부되면 UI 에 `{"reason":"device_not_ready","mcu":"HOMED"}` 가 전달되고
"장치 준비 중" 안내가 뜬다.

### D-05 · 압박점 확정은 장치가 주도한다

**결정**: `SCAN_RESULT` 를 받는 즉시 브리지가 `SET_CP_POINT` 를 보낸다.
사용자의 [확인] 버튼과 무관하다.

**이유**: 사용자가 버튼을 늦게 누르면 장치가 `CPR_READY` 에 못 올라가
다음 상태 진입이 막힌다. 화면 진행과 장치 준비를 분리해야 한다.

### D-06 · 통신은 JSON Lines, 라이브러리는 쓰지 않는다

**결정**: 한 줄에 JSON 하나. Teensy 측은 `saver_proto.h` 자체 파서.

**이유**: 시리얼 모니터로 눈으로 읽으며 디버깅할 수 있다.
프로토콜이 1단계 평면 구조라 ArduinoJson 이 필요 없고, 라이브러리 버전 문제도 없다.
PC 에서 `g++` 로 단위시험도 된다.
데이터량이 실제로 문제가 되면 그때 COBS/CBOR/바이너리로 바꾼다.

### D-07 · 측정 불가 필드는 0 이 아니라 생략한다

**결정**: 값이 없으면 필드를 통째로 뺀다.

**이유**: `0` 을 보내면 Jetson 이 "정상적으로 0" 으로 오해한다.
PPG 신호 품질이 나쁠 때 심박 0 과 미측정은 완전히 다른 의미다.

### D-08 · 심각도 3 오류는 정지가 먼저, 보고가 나중

**결정**: Teensy 는 모터를 끈 뒤에 `err` 메시지를 보낸다.

**이유**: 보고를 먼저 하면 그 사이 시리얼이 막혔을 때 모터가 계속 돈다.

### D-09 · 소프트웨어 정지는 물리 E-stop 을 대체하지 않는다

**결정**: E-stop 은 USB 와 무관한 하드웨어 회로가 모터 출력을 끊는다.
Teensy 는 그 사실을 보고만 한다.

**이유**: Jetson 이 죽어도, 시리얼이 끊겨도, 펌웨어가 멈춰도 정지해야 한다.

### D-10 · 제어 보드는 Teensy 4.1 (2026-08-03)

**결정**: Teensy 4.1. PCB 미발주.

**이유**: 이력의 회로도·펌웨어는 ESP32-S3 기준이었으나 발주 전이라 변경 비용이 없다.
Teensy 4.1 은 하드웨어 FPU 가 있어 제어 루프에 유리하고, 네이티브 USB 라
UART 브리지 지연이 없다.

**영향**: 핀 전면 재배정, `analogReadResolution(12)` 필요, PCB 재작성.
자세한 내용은 `teensy/reference/README.md` §2.

### D-11 · 압박점은 장치가 주행하며 찾고, 그다음 고정한다 (2026-10-01)

**결정**: 순서는 "주행 탐색 → 고정"이다. 바퀴로 선 상태에서 헤드를 접촉점보다 δ₀ 더 내려 높이를 유지하고, 후륜으로 정중선을 따라 이동하며 반력을 읽어 압박점을 정한 뒤, 안전핀을 빼 바퀴를 수납하고 음압으로 고정한다. 말단 판정, 압박점 계산(`D = 89.7 mm × EAPD / 205.8 mm`, 상한 95 mm), 목표 깊이 계산은 Jetson이 하고 Teensy는 요청을 실행·거부한다.

**이유**: 제출 보고서 3.3·6.2의 설계 순서다. 이전 상태머신(고정 S5 → 탐색)과 보고서가 어긋나 있었다. EAPD가 없을 때 대체 상수를 쓰지 않는다.

**남은 일**: `state_machine_v2.json`의 순서 변경은 v1.1 묶음에서 한다(한건민 합의).

### D-12 · 프로토콜 v1.1: 조회 외 모든 명령에 `bid`·`aid`, 정지 명령은 기록 사유로 막지 않는다 (2026-10-04)

**결정**: `PING`·`GET_STATUS`·`GET_INFO`·`GET_FAULTS` 외 모든 명령은 부팅 세션 `bid`와 늘어나기만 하는 번호 `aid`를 싣는다. Teensy는 가장 큰 `aid`보다 작은 옛 요청을 실행하지 않는다. `DRIVE_STOP`·`STOP_CPR`·`PAUSE_CPR`·`DISARM`은 줄·JSON·`t`·`cmd` 구조 검사를 통과하면 버전·상태·`bid`·`aid` 검사보다 먼저 정지 출력을 낸다. `RESUME_CPR`·`START_CPR`·`RESET_FAULT`·`VACUUM_OFF`는 예외가 아니다.

**이유**: seq 8개 기록만으로는 밀려난 옛 요청이 재실행될 수 있다(한건민 2·4차 지적). 정지를 기록 문제로 막는 것은 위험하고, 옛 정지 요청은 안전한 쪽으로만 움직인다. 반대로 옛 재개 요청은 AED 충격 중 압박 재개처럼 위험하다.

**기준 문서**: `docs/protocol_v1.1_draft.md` 7차 합의본. `protocol/` 반영 전까지 이 문서가 v1.1의 기준이다.

### D-13 · `DISARM`은 음압을 풀지 않고, 해제는 실제 확인 뒤에만 인정한다 (2026-10-04)

**결정**: 음압 출력이 켜져 있거나 해제가 확인되지 않았으면 `DISARM`은 압박·주행 출력만 끊고 `VACUUM_HOLD` + 재가동 금지(`rearm_lock`)로 둔다. 해제는 `VACUUM_OFF`나 수동 조작으로만 하고, 출력 꺼짐·압력센서 유효·해제 기준 압력 지속이 모두 성립해야 `vac_released = true`, `VACUUM_RELEASED`, `IDLE`이 된다. `ARM`도 `vac_released = true`를 요구한다. 판정값 3개는 10/6 실측 전까지 비워 두며 그동안 `ARM`은 동작하지 않는다.

**이유**: `motorsOff()`는 음압을 유지하므로 "항상 `IDLE`"은 상태와 하드웨어를 어긋나게 한다(한건민 5차). 체크밸브나 잔류 음압으로 출력이 꺼져도 흡착이 남을 수 있다(한건민 6차). 의학적 타당성은 **한성윤 확인 필요**.

### D-14 · Jetson은 세션 시작 seq를 무작위로 둔다 (2026-10-04)

**결정**: `TeensyLink`의 첫 seq는 1~65535 중 무작위다(`protocol.initial_seq`). v1.1 펌웨어와는 `GET_INFO`의 `last_seq`로 이어 간다.

**이유**: Teensy를 외부 5 V로 켜면(D-33) Jetson만 재시작될 수 있다. 1부터 다시 세면 직전 세션 seq와 겹쳐 새 명령이 ACK만 받고 실행되지 않는다. 모의 Teensy에서 재현했다(`tests/test_all.py` 6절).

### D-15 · UI는 받은 숫자만 보여 준다 (2026-10-04)

**결정**: 브리지에 연결되면 텔레메트리에서 받은 숫자만 표시하고, 생략·stale·비숫자 필드는 "—"로 둔다. 압박 횟수는 텔레메트리 필드가 없으므로 연결 중에는 "—"다. 모의값은 브리지 미연결(오프라인 시연)에서만 쓴다.

**이유**: 연결 중 측정 불가 필드가 오프라인 시연용 모의값(압박력 약 38~42 kg 등)으로 채워져 실측처럼 보였다. D-07(측정 불가 필드는 생략)과 v1.1 §3.3(생략 필드의 이전 값 재사용 금지)의 화면 쪽 짝이다.

## 기구·전기

### D-20 · 감속비 1.5 (2.0 아님)

**결정**: 타이밍 벨트 1.5:1.

**이유**: 2.0 이면 필요 회전수가 저전압 구간에서 부족했다.
1.5 로 낮추면 2,592 RPM 이면 되고 RPM 부족이 해소된다.
모터는 BL60120-2430 (Ke = 4.45 V/kRPM).

### D-21 · 볼스크류 후보는 1사이클 전체 프로파일로 검증한다

**결정**: 피크값 합산 방식은 쓰지 않는다.

**이유**: 피크 합산은 힘을 약 2.5배 과대평가한다. 후보가 잘못 탈락한다.

### D-22 · PETG-HF 는 준취성으로 다룬다

**결정**: FEA 에서 인장강도 하한값을 항복강도 대용으로 쓰고 안전계수를 추가한다.

**이유**: 명확한 항복점이 없다. **Z 방향 강도가 32% 감소**하므로
반복 하중을 받는 부품은 적층 방향을 반드시 고려해야 한다.

(2026-09-27) 실제 출력 재료는 PLA 다. 같은 원칙을 PLA 에 적용한다 — D-32.

### D-23 · 설계 목표 음압은 −22.5 kPa 이며 −30 kPa 는 도달 불가 (2026-09-08 근거 보강)

**결정**: 목표 −22.5 ±2.5 kPa (펌웨어, 2026-08-03 확정). 검증 합격선은 허용 하한 −20 kPa.

**이유**: 음압 블로워 BL6561-P(24 V) 팬 커브의 dead-head 정압이 약 27.3 kPa 라
−30 kPa 는 이 블로워로 물리적으로 도달할 수 없다. CFD 누설 해석
(`SAVER-docs/cfd/SAVER_CFD_results_final.csv`)에서 바닥 슬릿 갭 0.05~0.30 mm 의
운전점은 −27.0~−17.8 kPa 이고, −22.5 kPa 는 갭 약 0.19 mm 까지, 허용대역
−20~−25 kPa 는 갭 약 0.12~0.25 mm 에 해당한다. 초기 문서(중간보고서, ESP32 코드)의
−30 kPa 는 블로워 선정 전 목표였다.

### D-24 · "유지력 상한 290 N" 폐기 → 명목 유지력 3600 N (−20 kPa) (2026-09-08)

**결정**: 유지력은 F = ΔP·A_eff 로 표기한다. 1:1 명목 면적 0.18 m² 기준 −20 kPa 에서
3600 N, −22.5 kPa 에서 4050 N. A_eff 는 1:1 CAD 챔버 내측 치수로 확정한다(서정준).

**이유**: 290 N 은 dead-head 27.3 kPa 에 CFD 모델의 패드 면적을 곱한 값이다. CFD 그림
스크립트의 면적 상수(π·0.058² ≈ 106 cm², 반지름 58 mm 축대칭 원형 모델)로 2026-09-10 확인.
1:2 축척 추정이라는 초기 기록은 잘못이었다. 이 면적은 실제 300×300 mm 패드가 아니므로
유지력 상한으로 쓰지 않는다. 단, 같은 이유로 CFD 운전점(Table 6)도 모델 형상 기준이며
실제 패드(블로워 1대당 누설 둘레 약 3.3배, 2026-10-01 정정: 블로워가 챔버마다 1대)에서는 더 낮을 수 있다 → 재해석 항목.

**영향**: requirements R2, evidence C3, `report/02_design.qmd`, `tools/consistency_audit.py`
CHECKS 갱신. 보고서에는 명목 유지력을 `simulated` 로, 실측은 T1 이후 `tested` 로.

### D-25 · 시제품 축척은 1:1 (2026-09-08)

**결정**: 1:2 축척을 폐기하고 1:1 로 출력한다.

**이유**: 길이를 1/2 로 줄이면 면적·하중이 1/4 이 되어 T1 결과를 실기 값으로 환산할 수
없다. 보고서 v9 2.4.1·2.8.1 의 축척 서술은 삭제한다. FEA 모델 축척도 1:1 인지 확인한다.

### D-26 · 요구 최소 음압 산정 기준 (2026-09-08)

**결정**: 요구 최소 음압 = 최대 압박력 555.1 N × 안전율 2 / 명목 면적 0.18 m² ≈ −6.2 kPa.

**이유**: 이전 −5.6 kPa 는 500 N 기준이었고, 확정 최대 압박력 555.1 N 과 정합시킨다.
설계 목표 −22.5 kPa 는 요구의 약 3.6배로, 누설·표면 상태 여유다.

### D-27 · 블로워 최소 연속 운전 유량과 간헐 운전 (확인 조건부, 2026-09-08)

**결정(안)**: BL6561-P 의 최소 연속 운전 유량 400 L/min(제조사 자료 확인 전, 가정)을
밑도는 운전점에서는 연속 dead-head 운전을 하지 않는다. 블로워는 p_g 가 목표 −22.5 kPa
에 이르면 정지하고 허용 하한 −20 kPa 보다 약해지면 재기동한다. 목표에 도달하지 못하는
조건(예: 24 V·갭 0.20 mm 의 −21.8 kPa, 공칭 22.2 V)에서는 정지 조건이 성립하지 않으므로
도달 시간 상한(설정값) 안에 목표 미달이면 (a) p_g ≤ −20 kPa 이면 도달 압력을 유지 기준으로
삼아 대역을 [도달 압력, −20 kPa] 로 두고 (b) −20 kPa 미달이면 2-VU-004 로 보고·정지한다
(2026-09-10 보완). T1 은 정전압 24 V 조건으로 한정한다.

**이유**: 최소 연속 유량 400 L/min 과 dead-head(유량 0)는 동시에 성립할 수 없다.
400 L/min 에서 팬 커브 정압은 약 19 kPa 로 목표 −22.5 kPa 에 못 미친다.

**확인**: 데이터시트 원문(한건민), 제어 구현(한건민). 확인 전에는 `assumed`.

### D-28 · 시험 합격 기준의 출처 (2026-09-08)

T1 은 −20 kPa (허용 하한) 도달·유지. T2 는 깊이 ±5 mm, 속도 100~120 회/min
(W11 마네킹 시험 프로토콜·지침). 설계 목표(±2 mm, 110 ±2 회/min)는 합격 기준과
분리해 표기한다. 음압 도달 시간은 합격 기준이 아니며 실측 후 결정한다.

### D-33 · Teensy는 별도 벅 5 V로 켜고 USB는 통신에만 쓴다 (2026-10-04, 계획·미검증)

**결정**(한건민): 벅 컨버터 5 V를 만능기판을 거쳐 Teensy `VIN`/`GND`에 넣고, 뒷면 `VIN`–`VUSB` 패턴을 절단해 USB 전원과 분리한다. 검증 순서는 절단 뒤 도통 끊김 → 벅 무부하 전압 → Teensy 전원 → USB 통신이며, 분리 확인 전에는 외부 5 V와 USB를 동시에 연결하지 않는다.

**영향**: USB를 뽑거나 Jetson이 재시작해도 Teensy가 꺼지지 않는다. 통신 두절 동작(`T_comm`)이 실기에서 처음 작동하므로 안전 정지 시험에 USB 분리를 넣었고, Jetson은 D-14로 seq 충돌을 막았다.

**남은 확인**: 벅 입력을 E-stop 주접점 앞(제어 계통)에서 받는지. 뒤라면 E-stop 때 Teensy도 꺼져 보고하지 못한다.

**10/11 재확인 (팀장 위임, 신상현 검토)**: 10/7 한건민 제안(Teensy를 Jetson USB 전원으로 켜기)은 채택하지 않고 이 결정을 유지한다.
USB 전원이면 Jetson 재부팅이나 USB 분리 때 Teensy도 꺼져 통신 두절 동작(프로토콜 §9)이 작동하지 않는다(AGENTS.md 아키텍처 경계 4).
압박 VESC는 Teensy 지령이 끊긴 뒤에도 자체 timeout(미검증, 노이즈 대책 답변 10/5)까지 마지막 지령을 유지할 수 있다.
전류(Teensy 단독 약 100 mA)는 문제가 아니다. 벤치 시험만 USB 전원을 허용한다(VIN에 외부 5 V 동시 연결 금지).
남은 확인은 그대로다. 10/8 배선은 비상정지가 Teensy 전원도 끊으므로(정오표 48) 벅 입력이 주접점 뒤에 있다. 10/12 배선 때 앞으로 옮길 수 있는지 한건민이 확인한다.

### D-35 · AED 병행: 구조자 버튼으로만 멈추고, 자동으로 재개하지 않는다 (2026-10-04, 상태머신 v2.2, 검토 전)

### D-36 · 주행은 한쪽 엔코더 + 자이로 임시 모드로 G1, G2를 치른다 (2026-10-04, 초안 8차, 한건민 회신 반영해 합의)

**사정**: 주행 모터 1의 엔코더가 고장 났다(엔코더 전원선인 빨강·검정에 24 V 직결, 권선은 노랑–하양). 모터 1 본체는 정상이고, 모터 2는 본체와 엔코더 모두 정상이다(10/4 확인). 번호는 Teensy 핀 기준이다(모터 1 = BTS 7/8/15, 엔코더 11/12. 모터 2 = BTS 0/1/10, 엔코더 20/21). 국내 구매처가 없고 해외 교체품은 10/17~21 도착이라 G1, G2(10/14, 10/16)에 쓸 수 없다.

**결정**: 한건민 제안(한쪽 엔코더로 거리, WT901C 자이로로 방향, 좌우 출력 차등으로 직진)을 임시 모드로 채택하고, 프로토콜 초안 §4.7에 규칙을 둔다(`drv_enc_mode = 1`). 거리는 **모터 2 엔코더(20/21)**로 잰다. `drv_enc_side`는 모터 2가 달린 쪽이며, 좌우는 장착 상태로 확인한다.
- 방향은 지자기 없이 자이로 z축 적분. 정지 구간마다 영점 재추정
- 거리는 엔코더 바퀴 이동량을 차체 중심 이동량으로 보정(바퀴 간격 `drv_track_mm`)
- 자이로 끊김은 이 모드에서 심각도 3(`3-TU-011`). 좌우 차 검사 대신 방향 상한
- 장치가 `INFO`·`DRIVE_DONE`으로 모드를 알리고, Jetson 기록과 탐색 화면에 "단일 엔코더 + 자이로 (임시)"로 표시

**조건**(한건민 8차 회신 반영)
- 이 모드로 얻은 T3 결과는 그 조건을 붙여 표기한다. 교체 모터를 단 뒤 `drv_enc_mode = 2`로 되돌린다.
- 모터 1 엔코더는 선 색으로 특정하지 않고 엔코더 관련 선 4개를 전원, GND, Teensy에서 모두 분리해 각각 절연한다. 모터 1 권선(노랑–하양)만 BTS 모터 1 채널에 연결한다. 펌웨어는 11/12를 읽지 않고 인터럽트도 등록하지 않는다. 모터 두 대에 핀 기준 번호를 표시해 둔다.
- **지상 주행**(120 mm 반복, 모사체를 누른 상태의 방향 보정, T3)은 후륜 모터 전원을 직접 끊는 물리 비상정지와 제동 실측이 확인된 뒤에만 한다. 정지는 좌우 동시 정지 출력(PWM 0, EN LOW)이며, 능동 제동은 실측 전이다.
- 누적 방위 0은 `HEAD_HOLD drv_zero:true`에서만 잡고, 정지 구간에서는 자이로 bias만 재추정한다. 정지 판정 설정은 `drv_settle_delta_yaw_deg`(시간창 안 방위 변화량).
- 교체 모터(10/17~21 도착 예정)는 10/23에 단품 검사(권선 저항, 엔코더 출력 구조와 HIGH 전압) 뒤 장착한다. 15시 점검(좌우 엔코더 카운트 일치, 120 mm 반복, 탐색 3회)을 통과하면 `drv_enc_mode = 2`로 결선, 미달이면 기존 모터와 모드 1로 되돌린다(D-37). 기존 모터와 배선은 보관하고 교체 전 사진을 남긴다.

**수준**: 초안 규칙·Jetson·UI 표시·모의 Teensy `implemented`(모의). 펌웨어(WT901C 드라이버, 방향 보정, 인터록)는 한건민 `planned`, 10/11까지 벤치 시험 가능한 임시 기능. 메인 펌웨어에는 v1.1 주행 기능도 아직 없어 v1.1 전체 통합과 실물 주행 검증 날짜는 미정(초안 §10-17). 실물 미검증.

**S1 장치 상태표 (한건민 제안 그대로)**

| GET_STATUS 결과 | S1 처리 |
|---|---|
| `IDLE` | ARM 수락 확인 → HOME |
| `ARMED` | ARM 생략 → HOME (다시 ARM 하면 NOT_IDLE) |
| `HOMED` | ARM, HOME 생략. 원점 완료로 인정 |
| `FAULT`, `ESTOP`, 또는 `estop` 참, `faults` 있음 | `INIT_ERROR` → S10 |
| `VACUUM_HOLD`, `CPR_READY`, `CPR_RUNNING`, `CPR_PAUSED` | 자동 DISARM 하지 않고 `INIT_ERROR`(UNEXPECTED_MCU_STATE) |

- ARM이나 HOME이 거부되거나(ACK ok=false) 응답이 없으면(2-CM-002) 그 자리에서 `INIT_ERROR`. 이 명령들의 오류는 브리지의 일반 규칙(경고 → ERROR, 위험 → STOP)으로 처리하지 않는다. 그래서 Jetson의 ACK 무응답 오류에 `seq`를 붙였다.
- GET_STATUS 뒤 텔레메트리가 0.5 s(오래된 값 기준 `STALE_S`) 안에 오지 않으면 `INIT_ERROR`(NO_STATUS).
- `INIT_DONE` 전에 링크가 끊기면 다시 연결된 뒤 PING부터 다시 한다. 펌웨어 판(GET_INFO) 확인 전에는 보내지 않는다.
- 원점 대기 중 장치가 `FAULT`·`ESTOP`이나 `ARMED`·`HOMED`가 아닌 상태(재부팅 뒤 `IDLE` 등)가 되거나, `HOMING_DONE` 결과가 OK가 아니면 `INIT_ERROR`. 탐색 전 노드(X_MOVE, S2, X_CLOTHES, X_AED_PAD, S3S4, X_PPG)에서 `INIT_ERROR` → S10을 받는다. 새 필드 `error_return_by_event: {INIT_ERROR: S1}`로 어느 노드에서 났든 [재확인] 뒤 S1에서 처음부터 다시 점검한다. 다른 오류의 복귀 노드는 그대로다.
- 원점 시간 제한은 Jetson 설정 `home_timeout_s`(기본 비어 있음, 10/12 실측 뒤). 비어 있으면 시간은 검사하지 않고, 탐색과 흡착 진입은 X_SEARCH, X_PIN의 `requires_mcu: HOMED`가 막는다. 임의 값을 넣지 않는다.
- 브리지 없는 오프라인 시연과 체험판은 `offline_auto`(3 s)로 넘어간다. Jetson은 이 필드를 읽지 않는다.
- S10 원인 `init`: "장치 점검을 마치지 못했습니다 / 재확인을 누르면 처음 점검부터 다시 합니다", "비상정지 버튼을 확인하세요".

**Teensy 현황 (한건민 답변, 10/5)**: ARM 거부 사유는 ACK에 실린다(비상정지 3-MU-002 ESTOP_ACTIVE, 상태 불일치 2-CU-011 NOT_IDLE). 전압, 드라이버, 리미트를 포함한 ARM 인터록 전체는 아직 없다. HOME 실패 이벤트는 없고, 메인 코드는 HOME ACK 직후 HOMED와 HOMING_DONE을 보내는 골격이다(실제 원점 이동, 리미트, 시간 초과 판정은 구현 예정). RESUME_CPR은 CPR_PAUSED만 검사하고 음압, 압박점, 센서 유효성은 다시 보지 않는다. PAUSE_CPR은 정지 출력 → CPR_PAUSED → ACK, STOP_CPR은 정지 출력 → HOMED(현재 구현) → ACK 순서다. 다음 텔레메트리는 20 Hz 기준 보통 0~50 ms와 전송 지연 뒤에 온다. 압박 모터 VESC 정지와 기계 정착 확인이 아직 없으므로 **ACK는 물리적 정지 완료를 뜻하지 않는다**(D-45의 `pause_stop_verified` 유지).

**확인한 빈틈 (제안, 합의 전)**: S13에서 장치를 DISARM 한 뒤 [대기로](BACK_TO_IDLE)는 S2로 간다. 이때 장치는 `IDLE`이라 다음 사용에서 압박 위치 찾기(X_SEARCH, `requires_mcu: HOMED`)가 막힌다. BACK_TO_IDLE의 목적지를 S1로 바꿔 초기화 절차를 다시 거치게 하자고 한건민에게 제안한다(`protocol/` 변경).
→ 10/11 한건민 합의, v2.5 반영(D-47).

## 보고서·논문

### D-30 · ILCOR 인용은 이렇게 구분한다

ILCOR 은 기계식 CPR 의 **일상적(routine) 사용**을 권고하지 않는다.
그 이유는 **생존율 개선이 입증되지 않아서**이지, 장치에 문제가 있어서가 아니다.

SAVER 는 ILCOR 이 인정하는 **"특정 상황(specific circumstances)" 예외**를 겨냥한다.
구급대 도착 전, 다수 사상자, 일반인 구조자 상황이다.

**보고서에서 이 둘을 반드시 구분해서 쓴다.** 뭉뚱그리면 심사에서 "권고에 반하는
장치"로 읽힌다.
